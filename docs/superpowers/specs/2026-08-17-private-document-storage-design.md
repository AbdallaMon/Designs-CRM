# Private document storage and delivery design

**Date:** 2026-08-17  
**Branch:** `feat/workstage-flow-redesign`

## Problem

The legacy production implementation writes uploads directly into
`/home/dreamstudiio.com/public_html/uploads`. The hosting web server then exposes every
file at `https://dreamstudiio.com/uploads/...`. The FTP environment variables are not
what makes the files available: the active chunk and generated-PDF paths write to the
web root directly. The current branch retained the same security problem through an
Express static mount, a public `/v2/files/content/*` route, and a cache-first service
worker.

This makes client documents, chat files, contracts, signatures, and image-session
assets guessable/public and lets one browser account retain another account's cached
files.

## Locked design

1. The database stores one canonical reference format: `/uploads/<storage-key>`.
2. All physical files live below one absolute `ASSET_STORAGE_ROOT` outside the Git
   repository and outside `public_html`. Production's recommended root is
   `/home/dreamstudiio-storage`; local development defaults to a directory under the
   operating-system user's home directory.
3. `UPLOAD_DIR`, `TEMP_UPLOAD_DIR`, and `THUMBNAIL_DIR` remain supported as explicit
   compatibility overrides, but their defaults are derived from `ASSET_STORAGE_ROOT`.
4. There is no public static `/uploads` mount. A file is delivered only through a
   short-lived HMAC-signed `/v2/files/content/<key>` URL.
5. Signed URLs are capabilities. They are generated only after an authorized endpoint
   has selected the record. API responses expose signed access URLs while persistence
   continues to receive canonical `/uploads/...` references.
6. The signed-content endpoint validates expiry, signature, storage-key normalization,
   and containment below the configured storage root. It sends restrictive content and
   private-cache headers and supports normal HTTP range delivery through `sendFile`.
7. Backend PDF generation reads canonical uploads directly from private disk. It does
   not HTTP-fetch the application's own private files. Remote HTTP(S) fetching remains
   only for non-upload branding assets, with `IMAGE_DOMAIN` as the preferred base for
   root-relative legacy assets.
8. Generated PDFs are written through the same storage provider. The existing PDF
   renderer, fonts, layout, input values, and returned canonical DB paths stay unchanged.
9. Image-session reference data is available only to a valid image-session token or an
   authenticated user holding `image_session.admin.view`.
10. Socket payloads, emails, and Telegram attachment links receive signed access URLs;
    socket/API writes are normalized back to canonical storage paths.
11. The service worker deletes the old shared upload cache and stops caching protected
    documents. The browser's private HTTP cache remains available for signed URLs.

## Migration safety

- Database normalization and file copying are separate package scripts.
- Both scripts are dry-run by default.
- The file script copies and verifies; it never deletes the source.
- The database script updates only whole-value upload references (including values
  inside Prisma JSON fields), is idempotent, and emits a report before/apply summary.
- Production migration is user-run. The application does not move or delete production
  files during startup or deployment.
- Keep `public_html/uploads` as a read-only backup until the private route is verified.
  Direct web access to the old directory must be blocked at the hosting layer before the
  security cutover is considered complete.

## PDF behavior lock

The only allowed PDF-related change is asset I/O: load existing bytes from the private
storage provider and save the generated bytes to that provider. Rendering code and PDF
output logic remain untouched and are covered by the existing smoke tests.
