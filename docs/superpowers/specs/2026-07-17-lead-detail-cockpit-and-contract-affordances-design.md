# Lead-detail cockpit noise/height + contract-card affordances — design

**Date:** 2026-07-17
**Branch:** `feat/workstage-flow-redesign` (or a new branch off it)
**Status:** Approved, ready for planning

## Problem

Three unrelated pain points on the lead-preview / contract surfaces, batched because they touch the same detail views:

1. **The sales cockpit strip is too tall and too noisy.** The next-best-action strip
   (`SalesDealCockpit`) between the lead header and the tabs renders an *uncapped*,
   *unranked* list of action rows. A typical mid-pipeline deal fires ~6 rows (1 critical,
   5 warnings); worst case with a contract is ~9-10. It pushes the tabs 400-500px below
   the fold. The user's complaint is **both** height and noise.

2. **Contract stage labels only show on the in-progress stage.** In the contract stepper,
   the text label under each node only renders for the `IN_PROGRESS` stage. The user wants
   every stage to show its name + status.

3. **No quick "generate link" on the contract card.** The generate-signing-link action
   lives only inside the full `ViewContract` dialog. The user wants a quick action on the
   contract *card* that opens a dialog to generate/copy the link.

---

## Part 1 — Cockpit strip: rank, dedupe, and severity-aware collapse

The noise is generated by the rules engine, not the layout, so this fixes the cause
(backend ranking) and the symptom (frontend height) together.

### 1a. Backend rules engine — `server/src/modules/leads/lead/lead.cockpit.js`

All changes are inside the pure rules module. **No DTO/API contract change**: the frontend
already receives `severity` on the wire and the backend already pre-sorts. `priority` stays
internal to the sort.

**Kill the duplicate row.** `LEAD_STALE`'s firing condition is a strict superset of
`NO_UPCOMING_TOUCH`'s (same condition + "quiet ≥5 days"), so whenever `LEAD_STALE` fires,
`NO_UPCOMING_TOUCH` has already fired too — a guaranteed near-duplicate pair (both warning,
both "Schedule a call", same `OPEN_CALL` CTA, adjacent after sort). When `LEAD_STALE` fires,
suppress `NO_UPCOMING_TOUCH`. `LEAD_STALE` is the more specific/informative message, so it
wins. Mirrors the existing `staleFired` suppression of `FIRST_TOUCH_SLA`.

**Explicit warning-band priority.** Today ties within a severity band break on rule-emission
order (an artifact of source layout, not urgency). Add a `priority` number per warning type
and sort on `(severityRank, priority, emissionIndex)`. This matters more than before because
the top-ranked non-critical row is now *always visible* (see 1b). Ordering by decay speed:

| priority | type | rationale |
|---|---|---|
| 1 | `LEAD_STALE` | deal actively going cold; time-sensitive |
| 2 | `OFFER_AWAITING_DECISION` | money on the table, client-side clock running |
| 3 | `NO_UPCOMING_TOUCH` | nothing scheduled — next to go stale |
| 4 | `OBJECTION_UNHANDLED` | blocks close, doesn't decay on its own |
| 5 | `NO_PRICE_OFFER` | needs discovery first; rarely the true next step |
| 6 | `SIGNING_AWAITED` | waiting on someone else |
| 7 | `DISCOVERY_INCOMPLETE` | real work, slowest-burning |

**Make `ADVANCE_STAGE` reachable and promote it.** Today `hasBlocking = actions.length > 0`
gates `ADVANCE_STAGE`, so any single warning (e.g. the never-status-gated `OBJECTION_UNHANDLED`)
buries the one "move this deal forward" prompt, making it effectively unreachable mid-pipeline.
Change `hasBlocking` to "any **critical** fired". Then:
- If a critical is present → `ADVANCE_STAGE` stays suppressed (don't tell someone to advance a
  deal with an overdue call).
- If no critical is present → `ADVANCE_STAGE` sorts to the **very top** (above all warnings),
  so a clean-ish deal opens showing "advance the stage" rather than a warning. It keeps its
  `info` severity (color unchanged); only its rank changes.

### 1b. Frontend strip — `web/src/features/leads/cockpit/SalesDealCockpit.jsx`

**Visible floor = all criticals + the single top-ranked non-critical row.** With the ranking
above, that top row is `ADVANCE_STAGE` on a clean deal, otherwise the top warning. Everything
below the floor collapses behind a `⌄ N more suggestions` toggle.

```
┌─────────────────────────────────────────────┐
│  DealHealthBar (unchanged)                    │
├─────────────────────────────────────────────┤
│  🔴 Call overdue — call now      [Open call]  │  ← critical: always
│  🟡 Deal going cold — schedule…  [Schedule]   │  ← top non-critical: always
│         ⌄  4 more suggestions                 │  ← toggle, persisted
└─────────────────────────────────────────────┘
```

- Split the single `actions.map` into an always-shown slice (all criticals + first
  non-critical) and a `<Collapse>`-wrapped remainder in ranked order.
- The toggle row only renders when `hidden.length > 0`.
- Rows keep current styling — no per-row visual redesign, just the split.
- Severity is currently a pure color channel (only `SEVERITY_PALETTE[action.severity]`);
  nothing downstream breaks by slicing the list.

**Edge cases:**
- Many criticals (e.g. `PAYMENT_OVERDUE` + `CALL_OVERDUE`): all render, none hidden. The floor
  can exceed 2 rows — intended. Criticals are never collapsible.
- The existing "all caught up" / "deal closed" success callouts render when
  `actions.length === 0` and are untouched (collapse logic never reaches them).
- Default = collapsed (pref defaults to not-expanded), matching fullscreen/rail prefs.

### 1c. Preference — `web/src/features/leads/hooks/useLeadViewPreferences.js`

Add a third key using the existing `readBool`/`writeBool`/`makeSetter` helpers:

```js
const LEAD_COCKPIT_EXPANDED_KEY = "lead-cockpit-expanded";
// hook returns { …, cockpitExpanded, setCockpitExpanded }
```

**Global** (not per-lead), matching the existing fullscreen/rail prefs. Safe because criticals
+ the top row are always visible regardless of the pref, so the pref can never hide something
urgent. SSR-safe (reads in `useEffect` on mount). `setCockpitExpanded()` toggles.

### 1d. Cleanup — `web/src/features/leads/cockpit/config/cockpitActions.jsx`

Delete the dead per-type `severity` field from `COCKPIT_ACTION_CONFIG`. Nothing reads it
(`SalesDealCockpit` reads `action.severity` off the wire), and it's already stale/wrong for
`FIRST_TOUCH_SLA` (hardcoded `warning`; backend escalates to `critical` at 48h).

## Part 2 — Contract stage labels on every stage

**File:** `web/src/features/contracts/ContractStageStepper.jsx` (`StageNode`).

Today the label `<Typography>` (lines ~70-86) is gated by `active`, which is only true for
`IN_PROGRESS`. A per-stage `statusLabel` is already computed for all three statuses (lines
~34-39) but used only in the tooltip.

**Change:** render two lines under **every** node, not just the active one:
- **Line 1 — stage name** (`label`, may be Arabic).
- **Line 2 — status** (`statusLabel`: "Not started" / "In progress" / "Completed").

Keep the in-progress stage visually dominant so it doesn't drown in the others:
- `IN_PROGRESS` → bold + `primary` (as today).
- `COMPLETED` → `success` color, normal weight.
- `NOT_STARTED` → muted grey, normal weight.

Status values from `web/src/app/helpers/constants/contracts.js` (`STAGE_STATUS`):
`NOT_STARTED` / `IN_PROGRESS` / `COMPLETED`. Do **not** use `contractLevelStatus` (it colors
NOT_STARTED red — the stepper deliberately avoids it).

## Part 3 — "Generate link" quick action on the contract card

The generate-link logic lives inside `ContractBasics` in `web/src/features/contracts/ViewContract.jsx`:
- `generateSession(lang)` (lines ~255-267) → `POST shared/contracts/{id}/actions/generate-pdf-token`
  with `{ lang }` (ar/en), then `onReload()`.
- `buildSessionUrl(token)` (lines ~230-240) → `${origin}/contracts?token=...`.
- `copyToClipboard(text)` (lines ~242-248).

It's tightly declared as closures but has near-zero coupling to ViewContract internals (needs
only `contract.id`, `lang`, a local `setLoading`, the shared `handleRequestSubmit`, and an
`onReload`).

**Change:**
1. Extract the logic into a shared, self-contained piece — a
   `ContractGenerateLinkDialog` component (or a `useContractSessionLink(contract, onReload)`
   hook feeding a small dialog). It:
   - lets the user pick language (ar / en), mirroring the two `PdfBlock`s;
   - calls `POST shared/contracts/{id}/actions/generate-pdf-token`;
   - shows the generated `/contracts?token=...` link with a copy button.
2. Reuse it in `ViewContract` (same behavior as today).
3. Add an `FaLink` `Tooltip`+`IconButton` quick action in
   `web/src/features/contracts/ContractMenu.jsx` (alongside Clone / View / Cancel / Delete)
   that opens the new dialog. The card object already carries `arToken`/`enToken`/`pdfLinkAr`/
   `pdfLinkEn`, so no extra fetch is needed; on generate, refetch via the list's existing
   `fetchContracts`.
